# 협의 — 학교 커버 인구를 어디서 계산할까 (진우 ↔ 환)

**상황**: PR [#126](https://github.com/hjh8874/GreenLight/pull/126)(진우)과
[#127](https://github.com/hjh8874/GreenLight/pull/127)(환)이 **같은 게임 규칙**
— "학교가 커버하는 집은 인구가 늘어난다" — 을 서로 모르고 각자 구현했습니다.

파일이 달라서 **git은 충돌로 잡지 못합니다.** 둘 다 머지하면 인구가 두 곳에서 계산되고,
어느 쪽이 이기는지는 실행 순서가 정합니다.

---

## 결론 먼저 — 둘은 경쟁하는 게 아니라 서로의 빈칸입니다

읽어보니 **겹치는 부분이 거의 없습니다.** 각자 상대가 없는 절반을 갖고 있습니다.

| | #126 (진우) | #127 (환) |
|---|---|---|
| **정책** — 학교 하나가 몇 집을 감당하나 | ✅ `SchoolCoverageCapacity` | ❌ 없음 (무제한) |
| **공간 판정** — 어느 집이 근처인가 | ❌ 없음 | ✅ 맨해튼 반경 |
| **배치/철거 반응** | ❌ 없음 | ✅ `PlacedEvent` → 반경 재계산 |
| **총인구 배선** | ❌ 없음 | ✅ `CurrentPopulation` |
| **혜택 크기** | ✅ `CoveredPopulationCapBonus` | ✅ 고정 +2 |

**#126은 정책만 있고 기계가 없습니다.** `CalculateCoveredHouseCount(school, nearbyBuildings)`가
받는 `nearbyBuildings`를 **누가 어떻게 모으는지가 없습니다** — 위치 개념이 코드에 없습니다.
그리고 `BuildingEffectService`의 **소비자가 저장소 전체에 0건**입니다.

**#127은 기계만 있고 정책이 약합니다.** 반경 안이면 무조건 혜택이라, 학교 하나를 넓은 곳에
지으면 그걸로 끝입니다. **두 번째 학교를 지을 이유가 없습니다.**

---

## 제안 — 정책은 진우 것, 기계는 환 것

```
진우의 SchoolCoverageCapacity  →  환의 PopulationCalculator 안으로
```

구체적으로 `PopulationCalculator`의 계산을 이렇게 바꿉니다.

```
현재 (환):  반경 안이면 → 모두 +2

제안:      학교마다 반경 안의 집을 결정론적 순서로 모은다
           → 그중 앞에서 SchoolCoverageCapacity 채까지만 혜택
           → 나머지는 기본 인구 그대로
```

이러면 얻는 것:

1. **두 번째 학교를 지을 이유가 생깁니다.** 정원 8인 학교 하나로는 집 12채를 못 덮습니다.
   감사가 스쿨버스 카드에서 강조한 "커버 제한 = 두 번째 학교의 존재 이유"와 같은 논리입니다
2. **진우님 SO 필드가 실제로 살아납니다.** 지금은 값을 넣어도 시뮬레이션이 반응하지 않습니다
3. **환 쪽 배선을 그대로 씁니다.** 배치·철거 재계산, 세이브/로드 복원, 총인구 집계가 이미 동작하고
   테스트도 있습니다

버리는 것: 환의 "무제한 반경" 규칙 하나뿐입니다.

### 결정 필요한 하위 항목

- **정원 초과 시 누가 혜택을 받나** — 가까운 순? 배치 순? **결정론이어야 합니다**
  (세이브/로드·리빌드 때 값이 흔들리면 안 됩니다)
- **학교 2곳이 겹치면** — 지금 환 구현은 가산 1회만 줍니다. 정원을 각각 소비할지, 한 곳만 소비할지
- **혜택 크기** — 환은 고정 `+2`, 진우는 `CoveredPopulationCapBonus`(SO). SO 쪽이 낫습니다

---

## ⚠️ 그 밖에 #126에서 확인이 필요한 것

### 1. `BuildingDefinitionSO`를 되살리는 것이 맞습니까

이 SO 계열은 revert 커밋 `604166c`의 잔해로, **참조처가 미사용 레지스트리 1곳뿐인 죽은 코드**
였습니다. 시뮬레이션(`DemandMap`·`CommuteScheduler`)은 `TileType` 5종만 봅니다.

여기에 필드를 추가해도 **시뮬레이션은 아무 반응이 없습니다.** 되살려서 Sim에 잇는 작업이
별도로 필요합니다. 그 계획이 있으신지 확인하고 싶습니다.

### 2. `TileType.Hospital`을 추가했는데 받는 쪽이 없습니다

`CityFlowTypes.cs`에 `Hospital`이 추가됐지만 PR에 아래가 없습니다:

| 필요한 곳 | 지점 |
|---|---|
| `View/MainCityView.cs` | 색·크기·프리팹·스케일·오프셋 **12곳** |
| `UI/Panels/BuildPanelController.cs` | 빌드 버튼 |
| `Sim/DemandMap.cs` | `SinkTypes`·`CapacityFor` |
| `Sim/SimConfig.cs` | 용량 필드 (+ `.asset` 3개) |

지금 상태로는 병원을 **지을 수도 없고 지어도 안 보입니다.** 그리고 새 `TileType` 추가는
`SimEngine.RebuildSignals()`의 컬링과 얽혀 **로터리·신호가 함께 지워질 수 있습니다**
(준희·환 영역).

병원을 이번 빌드에 넣으실 계획이면 이 파급을 함께 잡아야 하고, 아니면 `TileType` 추가만
빼는 편이 안전합니다.

### 3. 폰트 에셋이 섞여 있습니다

`Assets/03_Art/Fonts/NanumGothic*`가 이 PR에 포함돼 있습니다. 병원·인구와 무관해 보이는데
의도하신 것인지 확인 부탁드립니다.

## 머지 순서 제안

```
1. #124 회전교차로   ← develop의 빨간 테스트 7건을 먼저 녹인다
2. #125 주차장       ← SimConfig·Contracts 파급이 가장 크다
3. #123 대기 차량 API
4. #126 ↔ #127       ← 이 문서의 협의가 끝난 뒤 함께
5. #130 회사 정원    ← #127 위에 쌓인 스택 PR
6. #129 스쿨버스     ← 학교 커버 정의가 확정된 뒤
```

**#129(스쿨버스)를 마지막에 둔 이유**: 스쿨버스는 "버스가 지나는 집 = 혜택"이라
**학교 커버 정의를 다시 건드립니다.** 이 협의가 안 끝난 상태로 머지하면 커버 계산이
세 곳이 됩니다.
