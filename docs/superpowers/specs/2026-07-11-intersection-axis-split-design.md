# 설계 — 교차로 축별 흐름 + 무신호 간섭 (신호 구매 피벗 1단계)

> 작성: 2026-07-11 (환 브레인스토밍). 짝 계획: writing-plans로 후속 생성.
> 선행: PR#38(코리도어 오버라이드) — 이 스펙의 §3이 그 코드를 전제. 머지 후 develop 기준 재배치 또는 스택 유지.
> 소속: **신호 구매 피벗 3단계 분해의 1단계**. 2단계(구매/배치/경제/UI)·3단계(마이그레이션/밸런스)는 별도 스펙.
> 후속(별도 스펙): 혼잡 인지 라우팅(증분 배정) — 건설이 진짜 퍼즐 수가 되게. 이 스펙과 독립(Assign/RoadNetwork vs Resolve).

## 배경 / 왜

게임 정체성 피벗: 신호 자동생성 → **유저가 신호를 구매·배치(방향+초 지정)**. 팀 구두 협의됨.

그런데 현재 엔진 수학에선 구매가 성립 안 한다:
1. **신호는 순수 손해** — 유효 용량을 듀티만큼 깎고, 그린웨이브(SignalFactor)는 최대 1(보너스 없음). 강제 자동생성이라 성립하던 게임.
2. **타일 flow가 축 미구분(합산)** — 구멍 2개:
   - 초록 레버 공짜: 듀티↑ = 타일 용량↑ = **양축 모두** 이득(화면은 교차 축 빨간불인데). "초록 최대"가 항상 정답 → "방향+초" 결정 무의미.
   - 오버라이드도 동일: 듀티 1이 교차 축까지 이득(보는 것≠버는 것).

**이 스펙 = 그 수학을 고치는 엔진 기초.** 자동생성은 유지(2단계에서 제거) — 축분리만으로도 초록 레버가 진짜 트레이드오프가 되어 현재 게임이 즉시 개선된다.

## §1. 흐름 수집 (FlowSolver.Assign)

- `_flow[]` 단일 배열 → **`_flowH[]` / `_flowV[]`** 두 flat 배열(SoA 유지, 틱 중 new 0).
- 경로 스텝의 축으로 분류해 적립: 가로 스텝(`dy==0`) → H, 세로(`dx==0`) → V, **대각 → 양축 0.5씩**(근사, 주석 명기).
- 타일 적립은 **진입 스텝** 기준(교차로에서 꺾는 경로는 진입 축으로 — 결정론적 단순 근사, 주석 명기).
- 경로 첫 타일(진입 스텝 없음)은 다음 스텝(출발 스텝) 축으로.

## §2. ratio 계산 (FlowSolver.Resolve) — 타일 유형별 4분기

C = `RoadCapacity`, d = `GreenRatio`(가로 듀티), λ = `UnsignaledInterference`:

| 타일 | ratio가로 | ratio세로 |
|---|---|---|
| 일반 도로(교차로 아님) | `(flowH+flowV)/C` (양축 동일 — 지금과 같음) | 〃 |
| 교차로 + 신호 | `flowH/(C×d)` | `flowV/(C×(1−d))` |
| 교차로 + 신호 + **오버라이드** | `flowH/C` | `flowV/C` (양축 풀 — §3) |
| 교차로 + 무신호 | `(flowH + λ×flowV)/C` | `(flowV + λ×flowH)/C` |

- "교차로" 판정 = SignalMap과 동일 규칙(직각 도로 이웃 ≥3). 무신호 교차로 = 교차로인데 SignalMap에 없음 — **자동생성 유지 중엔 라이브에서 미노출**(모든 교차로에 신호), 테스트로 검증 + 2단계 대비.
- 듀티 0 가드: 기존 규약 유지(초록 0 = 흐르면 최악 병목 `EfficiencyMinRatio`). `(1−d)=0`도 동일 처리.
- **경로 병목 판정: 그 타일을 건너는 축의 ratio** 사용(경로 스텝 축, §1과 같은 분류). 대각 스텝은 `max(ratioH, ratioV)`(양축을 다 쓰니 최악 축이 병목).
- 단일값 소비자(`GetRatio`/`GetCongestion`/`GetDensity01` → BurstDetector·CongestionNotifier·SimStats·차량 감속)는 **max(ratioH, ratioV)** 를 받음 — 인터페이스 무변경, 의미는 "그 타일의 최악 축". **이건 배관이지 화면 페인트가 아님**: 혼잡의 화면 표현은 차 중심 원칙(차가 밀리는 모습, 추후 경적 사운드 — 환 2026-07-11). 타일 색 강조는 넣지 않고, 현행 프로토 뷰의 도로 색칠은 에셋 전환 때 걷어낼 임시물로 취급.
- SignalFactor(그린웨이브)는 기존 축 무관 근사 유지 — 이번 스코프에서 손 안 댐.

## §3. 오버라이드 의미 변경 — 양쪽 초록 (PR#38 코드 위)

- **엔진**: 오버라이드 활성 신호 = 양축 `flow축/C`(위 표). 어떤 듀티 설정보다 좋은 3초 — "충돌 자체를 소멸시키는 정령의 힘".
- **페이즈**: `GetSignalPhase` 오버라이드 분기 → **양축 Green** (현행: 지정 축만 Green, 교차 축 Red). `IsSignalGreen`(축 버전) 자연히 양축 true → 코리도어에서 차가 아예 안 멈춤.
- **`Signal.OverrideHorizontal` 은퇴**: 페이즈·엔진에서 미사용. `TryOverrideSignal(tile, horizontal)`의 `horizontal`은 **코리도어 걷기 방향 전용**으로 의미 축소 — `ISignalControl` 주석 갱신(계약 시그니처는 불변).
- **뷰 파급(무변경으로 개선)**: MainCityView 속도 부스트가 축 무관 조회인데, 양쪽 초록에선 그게 정답이 됨(지난 리뷰 Minor #6 해소). 교차 축 차량도 부스트 — 의도된 연출.
- 무신호 교차로는 오버라이드 불가(현행 게이트 그대로 — SignalMap에 있어야 함). 2단계에서 "신호를 사는 또 하나의 이유"가 됨.

## §5. 파급 효과 (의도된 변화, 명시)

1. **초록 레버가 진짜 트레이드오프** — 초록을 몰면 교차 축이 실제로 막힘. 자동생성 상태에서도 현재 게임 개선("보는 것 = 버는 것" 회복).
2. **기존 delivered 수치 테스트 일부 값 변경** — 신호 교차로 듀티가 축별화되므로. 테스트 업데이트 예상(회귀가 아니라 의미 변경). 결정론 테스트는 불변이어야 함.
3. 오버라이드 delivered는 현행과 근사 동등(합산 듀티1 ≈ 양축 풀) — 손맛 재검증만.
