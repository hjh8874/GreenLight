## A. 채용 오버레이 (HiringStatusOverlay)

`BuildingConstructionOverlay`(#181)와 같은 구조 — 프리팹 하나, `ICityFlowServiceConsumer`,
끌어다 놓으면 배선 끝.

- **무엇을**: 정원 미달인 회사(Office) 앵커 위에 `채용중 {배정}/{총정원}` TMP 라벨.
  만석이 되면 라벨 제거. 철거·소실도 제거(조회 실패 = 제거, 공사 오버레이와 같은 정리 규칙)
- **데이터**: `IReadOnlyCityStats.TryGetCompanyStaffing(anchor, out CompanyStaffing)` —
  이미 public 계약. filled = 배정 수, capacity = 총정원. **계약 수정 0건**
- **발견**: `Placed`(Office, IsRemove 제외) + `Save.RestoreCompleted` + `Initialize` 시
  1회 전수 수집(앵커 필터) — 공사 오버레이가 오늘 검증한 3중 경로 그대로.
  공사 중(UnderConstruction)에는 staffing 조회가 false → 라벨 없음, 완성 `PlacedEvent`(실타입)에서 등장 — 공사 오버레이와 자연 릴레이
- **갱신**: `Update`에서 라벨 보유 앵커만 폴링(O(회사 수)). 위치 `GridToWorld` + XZ 카메라 빌보드
  (`FlowBurstFloatingText` 규칙 — #181 리뷰에서 확정된 그 코드)
- **프리팹**: `Assets/02_Prefabs/UI/HiringStatusSystem.prefab` — 루트에 컨트롤러 + 비활성 라벨 템플릿
- **소유권**: 전부 신규 파일(우리 계층). 남의 파일 수정 0건

## B. 지각 출근 (#182 머지 후 별도 브랜치)

`CommuteScheduler.SnapNewToHour`(신규 차 전용 훅)에서, 리빌드로 새로 생긴 차가:

```
CommuteWindow.InWindow(hour, car.DepartHomeHour, car.EveningStartHour) 이면
    → car.AwaitingNextWave = false   (그날 즉시 지각 출근 — 다음 틱에 Outbound)
그 외(퇴근창 안·그 이후)
    → 현행 유지 (다음 날 아침)
```

- `hour < DepartHomeHour`(출근 전 채용)는 현행도 그날 정상 출근한다 — 손대지 않는다
- 기존 차(건물 리빌드 생존자)의 `AwaitingNextWave` 의미는 그대로 — **신규 차 훅에서만** 완화
- #182 머지 후 필드명(`EveningStartHour`)이 이미 차 개별 값이라 유형별 창(야간조 공장 포함)에
  자동으로 맞는다 — 이 순서로 미루는 것이 구현도 더 단순해지는 이유
- 테스트: 낮 채용 → 즉시 출발 / 퇴근창 중 채용 → 다음 날 / 야간조(자정 넘김 창) 각 1건
