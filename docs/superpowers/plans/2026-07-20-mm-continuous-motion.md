# MM식 연속 차량 연출 전환 계획 (2026-07-20)

> 환 요구: **충돌(겹침) 없음 + 데드락 없음 + MM(Mini Motorways)급 자연스러움. 큰 손보기 허용.**
> 로컬 계획서 — 커밋 금지(docs/superpowers 스테이징 금지 목록).

## 1. 진단 — "잔재"가 아니라 구조적 한계다

심-뷰 일치 작업(3차 빌드 뷰 미러 + 이번 세션 속도 추종)은 됐다. 문제는 **일치시킬 신호 자체의 해상도**다.

Sim이 뷰에 주는 위치 신호의 전부:
- 일반 도로: `(타일, 진입방향 큐, 슬롯)` — 0.4초에 한 번 갱신
- 로터리 링: `slot=0` 고정 + 링 셀(=궤도 90° 단위)만 틱마다 회전 (RoadQueueNetwork.cs:212-219)

즉 **틱 사이 0.4초 동안 Sim은 아무 정보도 주지 않고**, 로터리는 90° 점프 신호다. 뷰가 이 신호를 아무리 충실히·부드럽게 따라가도(현재 속도 추종 모델) "목표 도달 → 다음 틱까지 정지"가 반복된다. 로터리 중간에 서는 건 이것이다. 겹침도 같은 뿌리: 큐가 (타일×진입방향 4개)인데 뷰 배치는 방향을 몰라 서로 다른 방향의 slot 0 두 대가 같은 좌표에 그려진다(계측 확정, 29be807).

**결론: "Sim이 위치의 주인, 뷰는 번역기" 구조를 유지하는 한 MM급은 불가능하다.**
MM은 반대다 — 차가 연속 공간의 주인이고, 시스템은 경로·수요만 정한다.

## 2. 제안 아키텍처 — "Sim = 관제탑, View = 운전사"

역할 재정의(헌법 §1 수정 필요 — 환이 오너 결정권):

| | 현재 | 제안 |
|---|---|---|
| 경로·수요·출발 | Sim | Sim (유지) |
| 용량·정체·안정도·경제·도착 코인 | Sim | Sim (유지) |
| **차량 위치·속도 (프레임 단위)** | Sim(틱 양자화) → 뷰 번역 | **뷰가 연속 소유** |
| Sim 위치의 역할 | 위치 그 자체 | **선두 상한(코리도)** — 뷰 차는 Sim 위치+1타일을 절대 앞지르지 못함 |

경제 불변식 보존: 코인은 여전히 Sim `ArrivalEvent`만. 뷰 차가 주차장에 몇 프레임 늦게 도착해도 수입은 Sim 기준(현재도 0.8타일 지연이 있고 문제없음).

### 데드락 불가 논증 (이 계획의 핵심 안전 장치)

과거 데드락 2종(dev-log-17)은 모두 **교차 관계의 정지 장치**(교차로 점유, 겹침 되감기)였다 — 정지 원인이 그래프에서 사이클을 만들 수 있었기 때문. 이 계획은 정지 원인을 딱 둘로 제한한다:

1. **같은 차선 앞차와의 간격** — 차선 내 차량은 거리순 선형 순서. 선형 체인은 사이클을 만들 수 없다.
2. **Sim 코리도 상한** — Sim 큐는 교착 밸브(GridlockValveTicks)로 항상 전진이 보장된다. 상한은 반드시 풀린다.

교차 차선·교차로·로터리의 충돌은 **정지가 아니라 기하 분리**로 해소한다(방향별 차선 오프셋, 로터리 연속 궤도). 서로 다른 차선의 차는 애초에 같은 좌표를 지나지 않으므로 세울 필요가 없다 → 세우지 않으므로 데드락 불가. "뷰 발명 정지 장치 금지" 교훈과 양립한다.

## 3. 실행 계획 — 3단계, 단계마다 계측 게이트

### Phase 1: 차선 기하 분리 (겹침 구조 해소) — 최우선
- `CarSnapshot`에 진입방향(`Dir Entry`) 추가 — Sim은 이미 안다(`TryLocateCar`의 direction, 현재 버려짐).
- 뷰 타일 내 배치 = `차선 오프셋(진입방향) + 슬롯 거리`. 양방향 도로의 좌·우 차선(laneOffset 0.18)은 이미 있음 — 교차로·타일 진입부까지 확장하는 것.
- 주차 진입도 동일: 슬롯별 접근 스퍼 분리(ParkingSlotOffset은 이미 슬롯별, 접근 경로가 공유라 겹침 — 스퍼 분기점을 슬롯별로).
- **게이트**: 겹침 계측(간격<0.25 쌍 분류)에서 교차방향·주차진입 유형 0건. EditMode 그린.

### Phase 2: 연속 주행 (앞차 추종 + Sim 코리도)
- 뷰 차량 프레임 주행: `desired = min(순항, 앞차간격 기반 속도, 코리도 상한 제동곡선)`.
  - 앞차 = **같은 차선 폴리라인 위에서 바로 앞의 뷰 차량** (Sim 슬롯이 아니라 뷰 거리순).
  - 코리도 상한 = Sim 스냅샷 위치 + 1타일 (지금의 목표 추종을 상한으로 완화).
- 현재 속도 모델(TravelSpeed·제동곡선·히스테리시스 브레이크등)을 그대로 재사용 — desired 계산만 바뀐다.
- 틱 사이에도 앞차가 움직이면 따라 움직인다 → 틱 양자화 정지 소멸.
- **게이트**: 정지상태 샘플 비율이 Sim 대기 비율과 일치(뷰가 임의로 더 세우지 않음 증명), 급정지 0, 지연 발산 없음, **데드락 워치독**(전 차량 60초 정지 감지) 0건.

### Phase 3: 로터리 연속 선회
- 링 차량: 90° 점프 신호를 버리고 뷰가 **연속 각속도로 선회**. Sim 링 셀은 "이 사분면을 지났어야 함"의 상한으로만 사용.
- 진출: Sim이 링에서 출구 큐로 옮긴 틱에 뷰는 궤도→출구 차선 접선 블렌딩.
- 링 위 차간: 같은 궤도의 선형 순서(각도순) — Phase 2와 같은 논증으로 데드락 불가.
- **게이트**: 로터리 통과 차량의 프레임 정지 0(진입 대기 제외), 궤도 위 겹침 0.

### 순서와 이유
1 → 2 → 3. Phase 1이 없으면 2에서 "앞차"의 정의가 모호해진다(차선이 없으면 누가 앞인지 없음). Phase 3은 2의 특수 케이스라 마지막.

- **건드리지 않는 것**: RoadQueueNetwork 자체(용량·밸브·신호·정체), 경제 전체, 세이브, 테스트 스위트의 Sim 계약.

- 리스크 2: MainCityView가 이미 2,600줄 — Phase 2에서 주행 로직을 `View/CarMotion.cs`(비-MonoBehaviour)로 추출 권장(시스템 감사 Task B와 방향 일치).

- 예상 규모: Phase 1 = 중(1세션), Phase 2 = 대(1~2세션), Phase 3 = 중(1세션).

## 4.5. Phase 1 착수 전 계측 (2026-07-20, 브랜치 HEAD 기준) — **계획 전제 반증**

Play 모드 라이브, 17대, 2400프레임(≈40초), 간격<0.25타일 쌍 분류 + 진입방향(TryLocateCar) 대조:

```
CROSS-DIR same-tile (교차 고스트)  : 0 pair-frames   ← 감사 당시 76건 = 겹침의 100%
CROSS-DIR diff-tile               : 0
SAME-LANE same-tile               : 0
SAME-DIR diff-tile (지연 붕괴)    : 102 pair-frames, min 0.112
parked/unlocated                  : 0

뷰 지연(TargetDistance - Distance): avg 0.989타일, max 2.000 (n=5108)
정지 샘플 비율(주행 중 차량)      : 0.898  (별도 900프레임 계측)
```

**해석**
- Phase 1이 겨냥한 **교차방향 겹침은 이번 세션 픽스(#3·#4·#6·#7·#8 + 속도 모델)로 이미 소멸**했다. 게이트 조건("교차방향·주차진입 유형 0건")은 **코드 변경 없이 이미 충족**.
- 남은 유일한 겹침은 **같은 방향·인접 타일**: 예 `car10(t(4,12),d=S,s0)` vs `car15(t(4,11),d=S,s0)` — 1타일 떨어져야 할 두 대가 0.112. 원인은 기하가 아니라 **뷰 지연 avg 0.99타일**(선두가 자기 목표에 못 미쳐 뒤차 머리 위치로 주저앉음).
- 지연·정지비율 0.898은 둘 다 **Phase 2(앞차 추종 + 코리도 상한)가 겨냥하는 것**이다.

**결론: Phase 1의 뷰 기하 작업은 현시점에 고칠 결함이 없다.** 다만 `CarSnapshot.Entry` 노출은 Phase 2의 "앞차" 판정(다른 경로가 같은 차선을 공유하는지 = (타일, 진입방향) 일치)에 필요하므로 **Phase 2의 입력으로 흡수**한다.

→ 제안: Phase 1 스킵(게이트 충족으로 종료), Phase 2 착수. **환 승인 대기** (AGENTS.md "계획과 코드가 어긋나면 임의 우회 금지").

## 4.6. Phase 2 구현 + 게이트 (2026-07-20)

### 구현 (전부 뷰. `CarSnapshot` 변경 0건)
`CarSnapshot.Entry` 추가는 **불필요**로 판명 — 차선 키 (타일, 진입방향)을 뷰가 자기 폴리라인에서
Sim과 동일한 식으로 유도할 수 있다(Sim `route[p]-route[p-1]` ↔ 뷰 `TileAt(p)-TileAt(p-1)`).

- `ResolveLaneLeaders()` — 매 프레임 차선 키를 만들고 앞차를 정한다. 앞차 = ①같은 차선 slot−1,
  ②내가 차선 선두면 다음 타일 차선의 꼬리. 둘 다 Sim 전진 순서를 따르는 선형 관계 → 사이클 불가.
  교차 차선 차량은 후보에 **들어오지 않는다**(기하 근접으로 세우면 교차 관계 = 데드락 재발).
- `TryGetLaneHeadway()` — 간격은 직선거리가 아니라 내 진행 방향 성분(코너 오탐 방지).
- 주행식: `desired = min(순항, √(2a·코리도여유), √(2a·앞차여유))`, 위치 클램프가 `TargetDistance` → **코리도**.
- 삭제: `TargetAdvancing`·`tickEdge`·`lastTickProgress` (코리도가 대체해 사용처 0).
- 노브: `vehicleCorridorTiles`(1.0), `vehicleMinHeadway`(0.55, **slotGap 상한 적용**).

### ⚠️ 계측 하니스 결함 2건 발견 — 감사 문서 §계측 재현 방법을 정정해야 함

**(1) 480Hz 앨리어싱.** `EditorApplication.update`는 **480Hz**, 게임 `Update`는 **60Hz**(실측).
프로브가 8샘플 중 7개를 "갱신 전 상태"로 다시 읽어 **정지비율이 구조적으로 ≈0.875로 부풀려진다.**
→ 계획 §4.5의 "정지 비율 0.898"과 그것이 뒷받침한 "틱 양자화로 차가 90% 서 있다"는 **사실이 아니다.**
실제 값은 0.066~0.125. 프로브는 `Time.frameCount` 변화 시에만 샘플링해야 한다.

**(2) 저부하 표본.** §4.5의 "교차방향 겹침 0건 → Phase 1 불필요" 판정은 주행차 4.19대 구간에서 나왔다.
5.9대 구간에서 재측정하면 **교차방향 겹침이 다시 나온다**(76~185 pair-frames, 최소 간격 0.000).
→ **§4.5의 Phase 1 스킵 권고는 철회한다. 차선 기하 분리는 여전히 필요하다.**

### 도중에 잡은 실패 1건 (기록)

종속시켜 노브가 Sim 배치와 모순될 수 없게 했다. 정원을 2로 낮추면 자동으로 0.5로 넓어진다.

### 4.6.1 환 라이브 피드백 1차 → 정지 원인 분류 (2026-07-20)

환: "심보다 앞서나가는 느낌은 없음. 아직 부자연스럽고 **앞에 차가 없는데도 갑자기 멈춰섬**."

정지 순간의 원인을 분류(1800 게임프레임):
```
앞차 없음 + 코리도 여유 0.000  : 487건 (81.4%)   ← 환이 본 것
앞차 때문                      : 111건 (18.6%)
```
**원인**: 코리도 상한을 *정지한 벽*으로 보고 `√(2a·여유)`로 제동했다. 그런데 상한은 틱마다
1타일씩 **전진하는 천장**이다. 움직이는 천장에 완전정지로 붙으니 "붙었다 멈춤 → 천장 점프 →
재출발"이 매 틱 반복. 앞차 판정도 같은 결함(간격 0.93타일인데 정지한 사례 관측).

**수정**: 상대 속도를 제동식에 넣는다 — `√(v_상대² + 2a·여유)`.
천장 속도 = `TargetAdvancing ? nominal : 0`(Sim이 잡고 있으면 진짜 벽), 앞차 속도 = 앞차 `TravelSpeed`.
이를 위해 4.6에서 "죽은 코드"로 지웠던 `TargetAdvancing`·`tickEdge`를 복원했다 —
**그게 원래 그 플래그의 존재 이유였고, 지운 것이 판단 착오였다.**

재계측 결과:
```
view stopRatio=0.096  sim heldRatio=0.027   지연 avg=0.876 max=2.861 (최고치)
정지 원인:  Sim이 잡고있음 58.8% | 앞차 13.1% | ★부당 28.1%
급정지 0, 워치독 최장 1.0초
```

## 4.10. "앞에 차 없는데 브레이크" 원인 규명 (2026-07-21, 환 라이브 2차 피드백)

### 원인 분류 계측 (감속>2.0/s 이벤트)
```
앞차 연쇄:        58.9%   ← 제동이 차간 간격을 타고 뒤로 전파
Sim 홀드:         35.8%   ← 신호 + 교차로 중재(틱당 1~2대만 통과) + 틱 0.4s 양자화
천장 톱니:         0.0%   ← 가설이었으나 반증됨
```
**"앞에 차 없는데 멈춤"의 정체 = Sim 홀드.** Sim이 한 틱(0.4s) 잡으면 뷰는 그걸 정직하게
번역해 세우고, 그 제동이 앞차 연쇄로 증폭된다. 뷰 결함이 아니라 **Sim 틱 양자화의 번역**이다.

### 시험 2건 (둘 다 계측으로 판정)

**(1) 연속 천장 + 버퍼 주행 — 기각.** 천장을 틱위상으로 보간하고 v² 부스트를 제거해
차가 천장 뒤 0.625타일 평형에서 달리게 했다. 결과: 감속 이벤트 106 vs 101/1k로 **개선 없음**,
뷰가 Sim 스냅샷보다 최대 2타일 앞서 **헌법 "Sim+1 상한" 위반**. 되돌림.

**(2) QueueSlot 스퓨리어스 targetChanged — 진짜 버그, 수정 유지.** 슬롯이 위치에서 빠졌는데
(§4.7) targetChanged 조건에 남아 있어, 슬롯이 바뀔 때마다 "목표 전진"으로 오판 →
**Sim이 잡고 있는 차에 v² 부스트가 들어가 몰래 앞으로 기어나갔다**(계측: maxDecel 85 스파이크,
뷰가 Sim보다 2타일 앞). 조건에서 QueueSlot 제거 + 안 쓰는 TargetQueueSlot 필드 삭제.

### 남은 브레이크의 근본 해법 — 전부 Sim 쪽 (환 단독 결정 가능, 다음 세션 후보)

## 4.12. 근본 원인 분석 — "신호 중간 정지 + 교차로 추월" (2026-07-21, 수정 없음·분석만)

환 라이브: "신호 중간에 서는 경우가 많고, 교차로 주변에서 뒷차가 앞차를 추월한다. 이대로는 안 된다."

### 계측 1 — 적색 대기 차량의 화면 위치 검증 (1200프레임, 1659샘플)
```
화면이 정지선(접근 타일)에 있음:      19.2%
화면이 적색 교차로 위에 있음:         25.8%  ★
화면이 그 외 위치(코너 경로상 1타일 앞): 55.0%
Sim 정지선 대비 초과 전진: avg 0.60타일, max 1.00 (정확히 코리도 한계)
예: car10 sim=(3,10)정지선 → 화면=(4,10) 적색 교차로 위, +1.00타일
```
**Sim은 차를 정지선에 정확히 세운다(진입 게이트는 작동함). 화면이 그 차를 최대 1타일 앞에 그린다.**

### 근본 원인 A — 코리도 +1타일이 홀드 상태에서도 유효하다
`corridor = Target + 1타일`은 **흐르는 교통**을 위한 여유다(틱 사이에 뷰가 앞서 달릴 수 있게).
그런데 Sim이 정지선에 잡아도(TargetAdvancing=false) 이 +1이 그대로 남는다 → 제동 곡선
√(2a·여유)는 **코리도**에 붙어서야 0이 되므로, 차는 정지선을 지나 교차로 한복판까지 굴러가서 선다.
**신호 진입 게이트(4.11)의 효과를 뷰의 코리도가 정확히 1타일만큼 무효화하고 있다.**
- 이산 천장+v² 부스트 조합은 이 초과 전진을 더 조장한다: 전진 중 여유 0까지 밀어붙이므로
  홀드가 걸리는 순간 이미 코리도(정지선+1)에 붙어 있다.

### 계측 2 — 추월 (3600프레임)
```
같은 차선(동일 타일·방향) 쌍의 역전: 1.1%, 온셋 1회(코너에서 0.03타일) — 무시 가능
차량별 평균 lag 범위: −0.57 ~ +2.22타일 (편차 2.79타일)
```
**같은 차선 안에서는 추월이 없다** (레버 A의 앞차 규칙이 작동함). 환이 보는 추월은 **차선 사슬
밖**에서 일어난다:

### 근본 원인 B — 뷰 위치 자유도(≈3.9타일 밴드)가 순서 보존 범위를 넘는다
차량별 lag이 −0.57~+2.22로 퍼진다(코리도 riding차는 Sim보다 앞, 제동 누적차는 2.2타일 뒤 —
따라잡기 +30% 상한이 회복을 느리게 함). 서로 **다른 타일**에 있는 두 차는 Sim 순서(타일 순)와
화면 순서가 어긋날 수 있고, 이 밴드(2.79타일)가 차간 간격(0.55)의 5배라 교차로 앞 감속·재가속
구간에서 화면 순서가 수시로 뒤집힌다. 앞차 규칙은 (타일,진입방향) 차선 사슬 안에서만 순서를
지키므로 이를 못 막는다:
- 교차로 진입부에서 다른 방향에서 온 차(다른 차선 키)와는 순서 제약이 아예 없다 → 통과·추월로 보임.
- 원인 A로 교차로 위에 서 있는 차 옆을 교차 초록 방향 차가 지나가는 것도 추월로 읽힌다.

### 종합 — 왜 "신호 체계 추가가 잘 안 되는가"
**부드러움(위치 자유)과 정확성(위치 정밀)의 정면 충돌이다.** Phase 2·레버 A는 틱 양자화를
숨기려고 뷰의 위치 자유를 계속 넓혔다(코리도 +1, 슬롯 제거, 따라잡기 밴드). 신호·교차로는
반대로 "차가 정확히 어디 서는가"를 요구한다. Sim이 옳게 계산해도 뷰가 ±1타일 오차로 그리면
신호는 화면에서 무너진다. **뷰 자유도의 상한이 '신호 앞 정지선'이라는 경계에서만은 0이어야 한다.**

### 수정 방향 (환 승인 대기 — 아직 안 건드림)
1. **홀드 시 코리도 붕괴**: TargetAdvancing=false면 상한을 Target(정지선)으로 — +1 여유는
   흐를 때만. 제동 곡선이 그대로 정지선에 세운다. 데드락 무관(정지 사유 불변, 위치만 정확해짐).
2. **lag 밴드 축소**: 홀드에서 풀린 차의 따라잡기 회복을 빠르게(정지 누적분 즉시 회복) —
   순서 어긋남의 원료인 편차 2.79타일을 좁힌다.
3. (관찰 후) 교차로 진입부 차선 키 경계의 순서 제약 — 1·2로 부족할 때만.
